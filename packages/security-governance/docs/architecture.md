# Architecture

This document describes the internal architecture of `@compilerai/security-governance`,
the module layout, the request/data flow through the system, and how RBAC, ABAC, and
the policy engine integrate to produce authorization decisions.

## Overview

`@compilerai/security-governance` is organized as a set of focused, single-responsibility
modules coordinated by a single `SecurityGovernance` facade. Every module depends only
on the shared `models.ts` type definitions and (where needed) on one collaborating
module — there are no cyclic dependencies and zero production runtime dependencies.

## Modules

### 1. API facade — `src/api/SecurityGovernance.ts`
The `SecurityGovernance` class is the single entry point. It constructs and wires every
subsystem in its constructor, exposes the 8 `ISecurityGovernance` methods, and adds
convenience methods for identity, compliance, telemetry, secret rotation, policy-rule
management, encryption helpers, and ABAC context/policy-rule factories. It also
cross-purposes subsystem output: every `authenticate` call emits telemetry and writes an
audit event; every denied `authorize` call writes an `auth_denied` audit event.

### 2. Identity — `src/identity/IdentityManager.ts`
Stores identities in a `Map` keyed by id, with a secondary index (`orgIdentities`)
grouping ids by `organizationId`. Provides `create`, `get`, `update`, `delete`, `list`,
`listByType`, `setStatus`, `exists`, and `count`. IDs are generated by
`generateIdentityId()` as `id-<counter>-<timestamp>` (base-36).

### 3. Authentication — `src/authentication/AuthenticationManager.ts`
A provider registry keyed by `AuthMethod`. Ships with a built-in `MockAuthProvider`
that validates an identity exists and is `active`, then mints a time-limited token
(1-hour TTL) stored in an internal map. Supports `registerProvider`, `authenticate`,
`validateToken`, `refreshToken`, and `getSupportedMethods`. Custom providers implement
`IAuthProvider`.

### 4. Authorization — `src/authorization/AuthorizationEngine.ts`
The decision engine. It performs a three-step evaluation per request:
1. **RBAC** — checks whether any of the request's roles grant the requested
   `resource`/`action` pair via `hasRolePermission`.
2. **ABAC** — if an `abacContext` is supplied, evaluates organization match,
   classification gating, time-of-day and day-of-week restrictions, and department tag
   overlap. Any ABAC denial short-circuits the decision.
3. **Policy** — delegates to the `PolicyEngine` for additional restrictions
   (`deny`, `require_approval`, `read_only`, `restricted`).

### 5. Policy engine — `src/policies/PolicyEngine.ts`
A priority-sorted, first-match-wins rule engine. Rules are matched against resource,
action, roles, and a `PolicyCondition` (organization, department, tags, time window,
days of week, classification, custom attributes). Each evaluation produces a
`PolicyEvaluationResult` containing the `decision` (a `PolicyEffect`), matched rules, a
human-readable reason, and a full `trace` of every rule considered. Also exports a
`createPolicyRule(...)` factory.

### 6. Roles — `src/roles/RoleDefinitions.ts`
Defines the 7 roles (`owner`, `admin`, `manager`, `employee`, `auditor`, `viewer`,
`ai_agent`), each with an explicit `RolePermission[]` allow-list over the resource
categories, plus a priority value. Exports `getRoleDefinition`, `getAllRoles`,
`getRolePermissions`, and `hasRolePermission`.

### 7. Secrets — `src/secrets/SecretsManager.ts`
`InMemorySecretStore` implements `ISecretStore` (store, retrieve, retrieveByName,
delete, list, update). `SecretsManager` wraps a store with a pluggable
encrypt/decrypt pair — in the facade, these are bound to `EncryptionService` so that
secret values are encrypted at rest as `iv:ciphertext`. Supports `storeSecret`,
`getSecret`, `getSecretByName`, `deleteSecret`, `listSecrets`, `rotateSecret`, and
`getSecretRecord`.

### 8. Encryption — `src/encryption/EncryptionService.ts`
Built on Node's `node:crypto`. Provides AES-256-CBC `encrypt`/`decrypt` (random 16-byte
IV, base64 output), SHA-256 `hash` (configurable algorithm), HMAC-SHA256
`sign`/`verify`, `rotateKey` (generates a new 32-byte key and sets it as current), and
`importKey` (validates 32-byte length). Keys are stored in an internal map keyed by id.

### 9. Audit — `src/audit/AuditLog.ts`
An append-only in-memory log implementing `IAuditLog`. `write` assigns a sequential
`audit-<n>` id and an ISO timestamp. `query` filters by `organizationId`, `actor`,
`action`, `result`, `startTime`, `endTime`, with `limit`/`offset` pagination (default
limit 100). Also exposes `getById`, `count`, and `export` (unbounded).

### 10. Compliance — `src/compliance/ComplianceManager.ts`
Seeded with control catalogs for ISO 27001 (5 controls), SOC 2 (4 controls), GDPR
(5 controls), and NIS2 (3 controls), all starting as `not_assessed`. Supports
`registerControl`, `getControls`, `assessFramework` (computes a 0–100 compliance score
and an overall status), `getAllFrameworks`, and `setControlStatus` (with optional
evidence).

### 11. Telemetry — `src/telemetry/TelemetryEngine.ts`
A lightweight in-memory event sink implementing `ITelemetryEngine`. The facade emits
events on authentication, authorization, policy evaluation, secret access, encryption,
and audit writes. Exposes `emit`, `getEvents`, `getEventsByType`, and `clear`.

### 12. Models — `src/models.ts`
All shared domain types and interfaces: `Identity`, `AuthCredential`, `AuthResult`,
`IAuthProvider`, `Role`, `ABACContext`, `AuthorizationRequest`/`Decision`, `PolicyRule`,
`PolicyCondition`, `SecretRecord`, `EncryptedData`, `Signature`, `AuditEvent`,
`ComplianceControl`, `TelemetryEvent`, and the `ISecurityGovernance` interface.

### 13. Barrel — `src/index.ts`
Re-exports the `SecurityGovernance` class, all concrete implementations, role helpers,
and every domain type for a single-import public surface.

## Data flow

A typical secure request flows through the package as follows:

```
caller
  │  createIdentity()  ─▶ IdentityManager.create()  ─▶ Identity
  │  authenticate()    ─▶ AuthenticationManager       ─▶ AuthResult
  │                        │  emits telemetry (success/failed)
  │                        │  writes audit (login success/failure)
  │  authorize()       ─▶ AuthorizationEngine.authorize()
  │                        ├─ RBAC: hasRolePermission(role, resource, action)
  │                        ├─ ABAC: evaluateABAC(ctx) ── org/class/time/day/tags
  │                        └─ Policy: PolicyEngine.evaluate() ── first-match-wins
  │                        │  emits telemetry (granted/denied)
  │                        │  writes audit (auth_denied) on denial
  │  storeSecret()     ─▶ SecretsManager ─▶ EncryptionService.encrypt() ─▶ SecretRecord
  │  getSecret()       ─▶ SecretsManager ─▶ EncryptionService.decrypt() ─▶ plaintext
  │                        │  emits telemetry (secret.accessed)
  │                        │  writes audit (secret_access)
  │  writeAuditLog()   ─▶ AuditLog.write() ─▶ AuditEvent
  │                        │  emits telemetry (audit.written)
  ▼
```

## RBAC + ABAC integration

RBAC and ABAC are evaluated sequentially within `AuthorizationEngine.authorize()`. RBAC
answers the question *"does any assigned role permit this action on this resource?"*
using the static permission tables in `RoleDefinitions`. ABAC answers *"do the
request's contextual attributes permit this action?"* using the supplied `ABACContext`.
The two are composable: a request may pass RBAC yet be denied by ABAC (e.g. a
classification restriction), and ABAC conditions can be enforced independently of the
specific role that granted the RBAC permission. Owner and admin roles bypass several
ABAC restrictions (business-hours write, weekend write, restricted classification),
reflecting elevated trust.

## Policy enforcement flow

When `AuthorizationEngine` reaches the policy stage, it calls
`PolicyEngine.evaluate()` with the same identity, resource, action, organization, roles,
and ABAC context. The policy engine iterates rules in descending priority order. For
each rule it checks resource, action, role, and condition matches; the **first matching
rule wins** and its `effect` becomes the decision. The engine then maps the policy
decision onto the authorization outcome:

| Policy decision | Authorization outcome |
|-----------------|-----------------------|
| `allow` | allowed (`matchedBy: 'rbac'`) |
| `deny` | denied (`matchedBy: 'policy'`) |
| `require_approval` | denied with `requires_approval` condition |
| `read_only` | denied for non-`read` actions; allowed for `read` |
| `restricted` | allowed with a `restricted` condition flag |

When no policy rule matches, the default decision is `allow`, deferring to the RBAC
result. This keeps the policy engine opt-in: organizations with no custom rules get
pure RBAC + ABAC behavior, while those that register rules layer additional governance
on top.
